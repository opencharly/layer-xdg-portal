# 2026.242.1648 — feat(xdg-portal): cover arch/cachyos, not just fedora

## Summary

The `distro:` cascade had only a `fedora:` section. Composing this candy onto an Arch or
CachyOS base therefore installed **nothing**, and the candy's own package checks failed the
build. Its `require:` list already names `pod-sway` and `pod-pipewire`, neither of which is
fedora-only, so the restriction reads as an omission rather than a decision.

The four packages carry identical names on Arch, so the new section is the fedora one
verbatim:

```
$ pacman -Si xdg-desktop-portal xdg-desktop-portal-wlr xdg-desktop-portal-gtk slurp
OK   xdg-desktop-portal
OK   xdg-desktop-portal-wlr
OK   xdg-desktop-portal-gtk
OK   slurp
```

`arch` covers cachyos as well, since the cachyos base declares `distro: [cachyos, arch]`.

### How it was found

Giving a punktfunk streaming host a capture path. A session resolves to `capture: Portal`,
so the host asks xdg-desktop-portal's ScreenCast interface to create a virtual output and
then receives frames over PipeWire. With no portal frontend the host installs, pairs and
negotiates a codec — every control-plane check passes — and then fails every session at
pipeline build:

```
create virtual output: ScreenCast portal on HEADLESS-2 failed: A portal frontend
implementing `org.freedesktop.portal.ScreenCast` was not found
```

Worth recording: the `env: XDG_CURRENT_DESKTOP: "sway"` this candy already sets is
**load-bearing**, and not only cosmetic. The frontend selects its backend from that
variable, and D-Bus activation does not supply it. With the packages installed but the
variable unset, the frontend activates on demand while the wlr backend never does, and the
interface is simply missing:

```
zbus::proxy: No such interface "org.freedesktop.portal.ScreenCast"
```

That also answers whether this candy needs a `service:` block: it does not. The portal ships
D-Bus activation files and respawns on demand — verified by killing it and watching the PID
change from 3252 to 3655 with nothing restarting it — provided `XDG_CURRENT_DESKTOP` is set,
which this candy does.

## How tested

```
$ charly box validate
rc=0
```

Validated with **charly `v2026.238.1242`**, the version this repo's `deploy.yml` pins and
builds, rather than a newer local binary — the repo's schema stamp is `2026.232.0520` and a
newer charly rejects it (`schema 2026.240.1943 is required`). Matching the binary to the pin
is what makes this the same gate CI runs.

Package availability confirmed on a live CachyOS venue with `pacman -Si` (output above), and
`xdg-desktop-portal` + `xdg-desktop-portal-wlr` were installed there successfully
(`install rc=0`) before this change was written, which is what established that the names
resolve on this base.

  `XDG_CURRENT_DESKTOP`, confirmed by inspecting `/proc/<pid>/environ` of the activated

- **R2 (no deferral)** — found while working on punktfunk; fixed here in the owning repo
  instead of worked around in the consuming box.

  the committed tree.
